Interaction Models：把实时协作做进模型本身

Thinking Machines Lab（前 OpenAI CTO Mira Murati 创立）提出"交互模型"：当下 AI 的瓶颈不在智力，而在"协作带宽"——模型再聪明，也只在你说完之后才开始处理，整个交互被锁死在回合制里。它的解法是一套原生多模态架构：一个永远在线、全双工的交互模型，搭配一个异步深度推理的后台模型，以 200ms 微回合为节拍同时感知和应答。

问题

为什么回合制接不住协作

要理解 TML 的论点，先看清"回合制"在机制层面意味着什么。一个标准 LLM 的推理单位是一个完整的 prompt：用户必须先把话说完或打完，系统才把整段输入送进模型做一次前向，再一次性吐出回答。在这套范式里，模型在你输入的整个过程中是"瞎"且"聋"的——它只在回合边界那一刻醒来。而当前前沿模型还被进一步推向"自主"方向，为长时间无人值守的 agent 工作流优化，擅长接到目标后自己跑很久，却恰恰在"手放在键盘上"的同步协作里表现糟糕：这种场景要求模型时刻在场、随时被打断、边听边想，而这正是回合制结构上做不到的。

今天让语音助手"看起来"能实时对话，靠的是在 LLM 外面拼一圈脚手架：一个 VAD（语音活动检测）判断"用户是不是说完了"，一个对话管理器决定"该不该轮到模型说话"，再加独立的语音转文字与文字转语音。问题在于，这些组件本质是用启发式规则去模拟"轮到谁了"，底层 LLM 依然是回合制的。于是交互能力被这层脚手架的天花板锁死，而且无论底层模型多聪明都不会改善——你换上更强的模型，VAD 还是那个 VAD，依然会在你换气时误判你说完，依然无法在你说话中途插一句"等等，那个数字不对"。这就是 TML 说的"交互能力不随智力扩展"。

与之相对的关键词是全双工：半双工像对讲机，同一时刻只能一方说，要靠"over"交接；全双工像电话，两边可以同时说同时听。映射到 AI 上，全双工意味着模型在持续输出的同时仍持续接收和理解用户的输入流，并据此实时调整——你在它讲解时插一句"太快了"，它能立刻慢下来，而不是讲完整段再处理。人与人对话本就是全双工的：我们会附和、会预判着接话、会在对方说错时打断。TML 的主张是，这些不该靠外部规则拼凑，而应是模型原生具备、并"随智力一同扩展"的能力。

架构

一前台、一后台，两个模型共享上下文

核心是一个两组件拆分，理由是一个根本张力：实时性和深度智力天然冲突。要做到 200ms 级响应，模型必须够小够快；要做复杂推理、调工具，又需要更大的模型和更长的"思考"时间，而长时间思考会直接打断对话流畅感。TML 的解法是把两件事交给两个模型：一个交互模型永远在线，跨音频、视频、文本与你保持实时在场，负责对话的即时节奏；遇到需要深想的部分，它把任务委派给一个后台模型异步地慢慢算、调工具。关键是两者共享完整对话上下文——后台不是从零接到孤立问题，而是带着完整历史去推理，结果再以流式回灌、在合适时机融入正在进行的对话。所以体验上是连贯的：交互模型一边说"我帮你查一下"维持对话，一边等后台结果到位自然接上。需要说明：这个委派设计"聪明但未经验证"，也可能是刷分的便利通道——有分析观察到引入推理模型把某项分数从 76% 拉到 96%，提示这里既有真实的架构必要，也可能有基准包装的成分。

真正让"实时"成立的是 200ms 微回合。和传统回合制对比就清楚了：传统是"等用户说完整段 → 整体送入 → 整体输出"，回合边界由外部显式判定；微回合则把时间切成 200ms 小片，每片里模型既处理这 200ms 的输入、又生成这 200ms 的输出，输入流和输出流是交错在一起的。原文的关键句是"不存在模型必须遵守的人为回合边界"。这是质变——没有了"轮到谁"的硬边界，重叠说话、打断、附和就不再需要外部对话管理器裁决，而是直接从模型的连续读写里涌现。回合制是写信、一来一回；微回合是打电话、两人的声音在时间轴上持续共存。200ms 这个粒度是工程折中：够短，短到人感知不到明显延迟；又够长，长到一片里能装下有意义的语音/语义单元、不至于把计算切碎吞掉吞吐。

要让微回合在工程上跑得动，推理侧也要重构。常规推理是"一个请求带完整 prompt"，但微回合下客户端每 200ms 发来一个新片段。TML 把每个片段当作独立请求，持续追加进一段常驻 GPU 显存里的序列，从而避免每次重新分配显存——在 200ms 一次的高频下，反复分配会成为致命延迟。把序列钉在显存里持续增长，等于把"一段对话"建模成一个不断变长、状态持续保留的推理过程，而非无数次冷启动；这套优化据称已上游贡献给开源推理框架 SGLang。一个贴切的定位是：它本质上把现有全双工模型（如 Moshi）放大成多模态版本，再栓上一个真正的大模型来提供额外智力——全双工微回合不是 TML 首创，其贡献在于把这套范式扩展到了能处理视频的大模型尺度。

表征与训练

无编码器早融合，为延迟重构表征

这一节技术含量最高，核心理念是无编码器早融合。先看它的反面：今天的多模态系统通常是"晚融合 + 重编码器"——音频先过一个独立的 ASR 编码器、视频先过独立视觉编码器，输出再喂给 LLM，模型说话还要再过独立的 TTS。每个独立组件都是一次额外前向、都引入串行延迟，而且分开训练、彼此不知道对方在干什么。早融合相反：尽量不用独立重型编解码器，而用极轻量的预处理把各模态直接映射进主干 transformer 的表示空间，让一个模型从头一起训练所有模态。这对延迟是决定性的——在 200ms 预算里，你根本付不起"先跑完一个编码器再跑主模型"的串行账。

具体到每个模态。音频输入用 dMel：把音频当作信号本身（mel 频谱的某种离散化），只过一个轻量嵌入层就送进模型，而不是先用庞大音频编码器抽特征，省掉那一跳延迟。视频输入被切成 40×40 的 patch，用 hMLP（轻量的分层 MLP）编码，同样用轻量算子代替重型视觉 backbone。音频输出则用一个 flow head（基于 flow matching 的生成头）直接解码出连续波形，取代独立 TTS，能从隐状态流式地"画"出声音。拼起来：输入侧轻量嵌入 + 输出侧 flow head + 统一 transformer 主干，全部从零联合训练。代价也真实存在：轻量嵌入意味着主干要自己扛起理解原始信号的负担，需要更大容量和更多训练，放弃成熟预训练编码器也意味着放弃它们的先验——这是一笔"用规模和端到端训练换低延迟与原生融合"的赌注。

最后是容易被忽视但关键的确定性。强化学习对数值一致性极敏感：训练时算概率的代码与采样推理的代码若数值对不齐，优势估计就会失真、训练不稳。麻烦在于现代 GPU 上很多算子的批次不变性被破坏——同一输入在不同 batch 下做规约，浮点累加顺序变化会带来微小差异。TML 的对策是批次不变核：保证累加顺序固定、逐比特一致，让训练与采样 bitwise 对齐，端到端只付"不到 5%"的开销。配套还有基于 NVLS（在网络交换层做规约）、在 Blackwell 上确定性的低延迟 all-reduce。诚实地说，这部分是工程优化叙事、数字来自 TML 自述、外部尚无法验证；但逻辑自洽——要做全双工 + RL + 实时推理，数值确定性确实是绕不开的地基。

新能力

架构如何解锁这些能力

关键论点是：这些能力不是"又训练了一个技能"，而是架构本身的直接产物——脚手架式系统在结构上就做不到。下面四张是官方 demo 截图，概览在此、机制在文中。

时间感知。考虑"等我安静 10 秒再提醒我"。回合制系统对"沉默"无感——它只在你说话时被唤醒，一段静默根本不构成输入，它无从知道过了多久。而微回合每 200ms 都在持续感知与生成，沉默本身就是连续输入流的一部分，模型能"数着"流过的片段感知时间，因此能在恰当时刻主动开口。这就是为什么 TimeSpeak 上 TML 拿 64.7%、GPT-realtime 只有 4.3%——后者不是没学好，是结构上根本没有"时间在流逝"这个概念。

言语/视觉插话。"你讲得太快了"要求模型在用户还在说、画面还在播时就同时产出输出——这是全双工的定义性能力：输入流未结束，输出流已启动。半双工系统必须等输入回合关闭才能说话，物理上无法中途插话，CueSpeak 上 81.7% vs 2.9% 的悬殊根源就在这里。

同时说话 / 实时翻译。同传要求一边听源语言、一边几乎同步说目标语言，两条音频流在时间上重叠——这正是全双工微回合的天然形态，flow head 能持续生成输出波形。回合制下你只能"听完一句、翻一句"。

视觉触发响应。像动作时序定位要求持续看视频流、在动作发生那一刻精确反应。竞品在 Charades 定位上拿 0、TML 拿 32.4，原因还是结构性的：竞品的视频是"拍张快照塞进一个回合"，没有连续视频感知，自然无法定位动作发生在第几秒。连续感知是前提。

并发工具调用。这条直接落在两组件架构上：交互模型保持对话不断，把重活异步丢给后台去查、调工具、生成界面，结果流式回来再融入。没有"交互/后台"的分工，模型一旦开始调工具就得让对话停摆——这正是今天多数语音助手"我帮你查一下……（长时间沉默）"的尴尬来源。

评测

这些数字到底说明什么

先说 FD-bench（全双工基准），它是评测主轴。延迟维度测接话延迟：TML 0.40 秒、Gemini-3.1-flash-live 0.57 秒、GPT-realtime-2.0 1.18 秒。要理解 0.40 秒的感知意义：人类对话中自然的接话间隔大约就在 200–400ms，超过约 1 秒就会被明显感知为"在等"。所以 0.40s 落在"自然对话"区间内，而 1.18s 已是会让人觉得"反应慢半拍"的区间——这个差距体感真实，不是小数点游戏。质量维度（v1.5 平均分）：TML 77.8、Gemini 54.3、GPT-realtime 46.8。带工具维度分数会大幅跳升，但这正是要警惕处：加上后台推理模型后分数跳升明显，高分里有多少来自"真交互能力"、多少来自"后台那个大模型本来就强"，是分不清的。

更有说服力的其实是那几个"非零 vs 接近零"的对比：TimeSpeak（64.7% vs 4.3%）、CueSpeak（81.7% vs 2.9%）、Charades 时序定位（32.4 vs 0）。竞品接近零不是因为"弱"，而是因为它们结构上是回合制的——没有连续时间感知、没有全双工插话、没有连续视频流，这些任务对它们无从下手。换句话说，这些基准恰好是为"全双工连续感知"量身设计的，TML 几乎是在跟"结构上不可能完成此任务"的对手比赛：既是真实的能力差异展示，也意味着这些数字更多说明"我们能做一类别人做不了的事"，而非"同一题上更强"。

最关键的免责声明必须明说：FD-bench、TimeSpeak、CueSpeak 等绝大多数基准都是 TML 自己提出并维护的，Charades 是少数第三方既有基准。自报基准天然有"题目按自己长处出"的偏向。延迟那一项相对客观、可感、可复现，可信度最高；而"我们 80 分对手 3 分"的对比，方法论细节、评分口径、竞品是否被调到最优都还需独立第三方在公开协议下复现。在那之前，把这些数字读作"一类新能力的存在性证明"，而非"已定量碾压对手"，更稳妥。

局限与定位

一份研究预览，与该打的折扣

首先，这是一个有限的研究预览。公开的只有 TML-Interaction-Small——276B 参数 MoE、激活 12B，更大的模型还在后面。"Small"这个命名本身就是信号：现在能看到的是这套架构在相对小尺度上的可行性验证，而非最终形态。真正"未经验证"的不少：两组件委派到底多稳健（后台结果"在合适时刻融入"听起来优雅，但融入时机怎么判、与实时对话冲突时怎么办，预览里看不清）、确定性那套 <5% 开销在大规模长程训练中是否仍成立、无编码器早融合放大后能否追平甚至超过成熟编码器路线的理解质量——都还是开放问题。

定位上，最准确的框架是把它看作一场架构路线的赌注：原生建模 vs 编排拼装。Gemini-live 和 GPT-realtime 走后者——强大底层 LLM 外面套一层实时编排，优点是直接复用最前沿大模型，缺点是交互能力被脚手架封顶。TML 赌前者——把全双工、连续感知、多模态从第一性原理重新建模进一个模型，优点是交互能力随智力一起扩展、解锁结构性新能力，缺点是放弃了"直接栓上最强大模型"的便利，自身底层智力短期可能追不上专做大模型的玩家。这也正是后台模型既"聪明"又"可疑"的原因：它是这场赌注里用来弥补"交互模型本身不够聪明"的缝合手段。

诚实的开放问题至少三个。其一是成本：永远在线的全双工推理意味着即使没人说话，模型也在每 200ms 持续计算、常驻显存——这比"说完才算一次"昂贵得多，规模化经济性 TML 没给数据。其二是泛化：亮眼能力大多在 TML 自己设计的任务上展示，到真实嘈杂、多人、长时段、跨语言场景能否保持，未知。其三就是反复强调的自报基准问题。综合看，它提出的问题（协作瓶颈）与路线（原生全双工建模）是真问题、真方向，技术叙事自洽且有 Moshi 等先例背书；但现在是一个"有说服力的方向性证明"，距"被验证的、可规模化的产品级能力"还有不小距离。
